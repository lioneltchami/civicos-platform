# Item 03 — Scheduler durable-wiring remediation code review

**Date:** 2026-08-19
**Stage:** 2 of 4 — two fresh blind focused code reviews
**Scope:** Internal durable dispatch, local runtime evidence, and local fakes only. No staging, official suite, real recipient, credential, deployment, certification, or submission work is authorized.

## Review conclusion

Both blind reviewers agree that the safest implementation is **additive**. The current schedule-level `GovStackAlertSchedule.dispatched` field must not remain the sole delivery authority, but it should be retained as a compatibility projection while migration-backed recipient work and an outbox become authoritative. The pure state-machine prototype, URL safety controls, bounded transport settings, post-commit scheduling, and no-network-I/O-under-lock discipline must remain intact.

> The implementation must model **at-least-once task execution**, not claim exactly-once recipient delivery. A durable recipient idempotency boundary, conditional claim/lease state, and provider/fake correlation keys are required to make duplicate tasks and recovery converge safely.

## Mandatory compatibility and safety rules

| Rule | Requirement |
|---|---|
| Public Scheduler contract | Do not change existing URL paths, response shapes, validation, authorization, route inventory, or legacy schedule CRUD semantics merely to support remediation. |
| Existing safe transport | Retain URL validation/allowlisting, bounded timeouts, no redirects, redacted logs, and no outbound I/O while a database lock is held. |
| Existing pure prototype | Do not replace or silently repurpose `delivery_state.py`; add the durable adapter and preserve current unit tests. |
| Legacy Boolean | Retain `dispatched` during rollout as a compatibility/aggregate field only. New recipient execution gates must use durable generation and delivery state. |
| Transaction boundary | Create delivery and outbox state in the origin transaction. Publish only after commit. Broker publication and HTTP transport must be recoverable and outside DB lock ownership. |
| Privacy and authority | Keep recipient-sensitive data, messages, raw URLs, tokens, and arbitrary exception text out of delivery/outbox operational state and status responses. Scheduler fakes may not mutate Payments/Consent-owned records. |
| Evidence boundary | All added runtime traces and fakes are local-only. They must not be presented as staging, external recipient, official test, conformance, certification, or submission evidence. |

## Stage 2 acceptance gate

Stage 3 must not be considered internally complete until the code and tests demonstrate that recipient work is created durably, outbox publishing is recoverable, duplicate workers are fenced by durable claims, all required lifecycle transitions persist, all 37 operation IDs have local runtime evidence, cross-BB fakes are deterministic/authority-preserving, and the operational status projection is tenant/owner safe and non-PII.
